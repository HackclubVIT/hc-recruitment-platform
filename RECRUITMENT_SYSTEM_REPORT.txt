1. SYSTEM OVERVIEW
================================================================================

The HC Recruitment Platform is a role-based web application for managing the
complete recruitment lifecycle at HackClub VIT Chennai. It serves as a companion
system to the main HackClub website, handling everything from application review
to final hiring decisions.

PURPOSE:
- Streamline recruitment workflow for Leads, Recruiters, and Panelists
- Provide department-scoped access control
- Automate interview scheduling with conflict detection
- Track application status through a defined state machine
- Generate analytics and export capabilities

TECH STACK:
- Frontend: Next.js 15 (App Router), React 18, TypeScript
- Styling: Tailwind CSS with custom design system
- Database: Prisma ORM (SQLite dev, PostgreSQL prod)
- Authentication: JWT tokens proxied from main site
- Email: Nodemailer (Gmail SMTP) with console fallback
- Testing: Vitest

2. ROLE-BASED ACCESS CONTROL (RBAC)
================================================================================

ROLE HIERARCHY (highest to lowest):
  ADMIN > LEAD > RECRUITER > PANEL > CANDIDATE

DEPARTMENT SCOPING:
- ADMIN: Access to all departments
- LEAD: Access only to their assigned department(s)
- RECRUITER: Access only to their assigned department
- PANEL: Access only to assigned interviews

PERMISSION MATRIX:

| Action                    | ADMIN | LEAD | RECRUITER | PANEL |
|---------------------------|-------|------|-----------|-------|
| View all departments      | YES   | NO   | NO        | NO    |
| Manage recruiters         | YES   | YES  | NO        | NO    |
| View analytics            | YES   | YES  | NO        | NO    |
| Schedule interviews       | YES   | YES  | NO        | NO    |
| Make final decisions      | YES   | YES  | NO        | NO    |
| Update application status | YES   | YES  | LIMITED   | NO    |
| Bulk update status        | YES   | YES  | YES       | NO    |
| Add notes                 | YES   | YES  | YES       | YES   |
| View assigned applications| YES   | YES  | YES       | YES   |
| Submit feedback           | YES   | YES  | YES       | YES   |

STATUS TRANSITION PERMISSIONS (enforced by canTransition()):

  APPLIED → UNDER_REVIEW, REJECTED                    [RECRUITER, LEAD]
  UNDER_REVIEW → SHORTLISTED, ON_HOLD, REJECTED      [RECRUITER, LEAD]
  ON_HOLD → UNDER_REVIEW, REJECTED                   [RECRUITER, LEAD]
  SHORTLISTED → INTERVIEW_SCHEDULED, REJECTED        [LEAD only for scheduling]
  INTERVIEW_SCHEDULED → INTERVIEWED, SHORTLISTED     [LEAD only]
  INTERVIEWED → SELECTED, WAITLISTED, REJECTED       [LEAD only]
  WAITLISTED → SELECTED, REJECTED                    [LEAD only]
  SELECTED → (terminal)                              [none]
  REJECTED → (terminal)                              [none]

NOTE: ADMIN role is implicitly allowed via requireRoles guard but not explicitly
listed in ROLE_TRANSITION_PERMISSIONS - this is a known bug.

3. APPLICATION STATE MACHINE
================================================================================

The recruitment pipeline follows a strict finite state machine defined in
lib/status.ts:

VALID TRANSITIONS:
  APPLIED
    └──> UNDER_REVIEW
    └──> REJECTED

  UNDER_REVIEW
    └──> SHORTLISTED
    └──> ON_HOLD
    └──> REJECTED

  ON_HOLD
    └──> UNDER_REVIEW
    └──> REJECTED

  SHORTLISTED
    └──> INTERVIEW_SCHEDULED
    └──> REJECTED

  INTERVIEW_SCHEDULED
    └──> INTERVIEWED
    └──> SHORTLISTED (reschedule/cancel)

  INTERVIEWED
    └──> SELECTED
    └──> WAITLISTED
    └──> REJECTED

  WAITLISTED
    └──> SELECTED
    └──> REJECTED

  SELECTED, REJECTED = TERMINAL (no outgoing transitions)

ENFORCEMENT:
- Frontend: getValidNextStatuses() filters dropdown options
- Backend: canTransition() validates every status change in API
- Database: No constraints (enforced at application layer)

4.1 LEAD DASHBOARD (app/(dashboard)/lead/dashboard/page.tsx)

  RECRUITERS TAB:
  - Recruiter team table with department badges
  - Active application counts per recruiter
  - API: GET /api/lead/recruiters

  SCHEDULING TAB:
  - Placeholder UI for interview scheduling guidance
  - Links to Applications tab for candidate selection
  - InterviewSchedulerModal integration

  ANALYTICS TAB:
  - Funnel visualization with counts
  - Panel workload (upcoming interviews)
  - Feedback recommendation distribution
  - API: GET /api/lead/analytics

APPLICATION DETAIL MODAL (shared with Recruiter):
- Basic info, skills, answers (parsed from JSON)
- NotesThread (real-time notes via /api/recruiter/applications/[id]/notes)
- StatusHistoryTimeline (audit trail)
- Interviews list with feedback preview
- FeedbackSummary (loads on demand via /api/lead/applications/[id]/feedback)

4.2 RECRUITER DASHBOARD (app/(dashboard)/recruiter/page.tsx)
-------------------------------------------------------------
Simplified interface focused on application processing:

- ApplicationTable (scoped to recruiter's department, no dept filter)
- Bulk selection with bulk status update dialog
- Application detail modal (read-only interviews, no scheduling)
- Status change dropdown with role-validated transitions
- Fixed navbar (known bug: pt-20 may not match actual height)

4.3 INTERVIEW MANAGEMENT (Lead only)
------------------------------------
Full CRUD for interviews via /api/lead/interviews:

  SCHEDULE (POST):
  - Select candidate (SHORTLISTED apps)
  - Pick panelists (PanelistPicker component)
  - Set date/time, mode (ONLINE/OFFLINE), location/link
  - Conflict detection: panelist double-booking + candidate conflicts
  - Email notifications to candidate + panelists

  RESCHEDULE (PATCH action=reschedule):
  - New time, optional panelist changes
  - Conflict re-check
  - Email notifications

  CANCEL (PATCH action=cancel):
  - Status → CANCELLED
  - Email notifications

  COMPLETE (PATCH action=complete):
  - Status → COMPLETED
  - Enables feedback submission

  PANELIST AVAILABILITY:
  - getPanelistAvailability() shows busy/free for time slot
  - Used by InterviewSchedulerModal

4.4 FEEDBACK SYSTEM
-------------------
- Panelists submit feedback on COMPLETED interviews
- Ratings (technical, communication, problemSolving, cultureFit: 1-5)
- Overall score (0-100)
- Recommendation: STRONG_HIRE, HIRE, MAYBE, NO_HIRE
- Comments optional
- FeedbackSummary aggregates for Lead decision making
- Decision requires feedback unless override checked

4.5 NOTIFICATIONS
-----------------
Real-time in-app notifications via Notification model:

TYPES:
- APPLICATION_SHORTLISTED
- INTERVIEW_SCHEDULED
- INTERVIEW_RESCHEDULED
- INTERVIEW_CANCELLED
- DECISION_MADE
- FEEDBACK_SUBMITTED

FEATURES:
- Unread count badge
- Mark as read / mark all read
- Paginated list (50 per page)
- Created in same transaction as triggering event

5. API ARCHITECTURE
================================================================================

All API routes use Next.js App Router with authentication guards:

AUTHENTICATION FLOW:
1. Client calls /api/auth/login with email/password
2. Server proxies to MAIN_SITE_API (/api/auth/login)
3. Main site returns JWT
4. Server sets httpOnly cookie + returns token
5. Client stores token in localStorage
6. Subsequent requests include Authorization: Bearer <token>
7. authenticateRequest() verifies JWT, fetches fresh user from DB

GUARDS (lib/guards.ts):
- authenticateRequest(): Token verification + user fetch
- requireRoles(...): Role authorization
- requireDeptAccess(): Department scoping
- requireApplicationAccess(): App-level department check
- requireInterviewAccess(): Interview-level department check

LEAD ENDPOINTS (/api/lead/):
  GET  /dashboard              - Dashboard stats
  GET  /recruiters             - Recruiter list with workload
  GET  /analytics              - Funnel, panel workload, recommendations
  GET  /interviews             - Interview list (filters: status, applicationId)
  POST /interviews             - Schedule new interview
  PATCH /interviews/[id]       - Reschedule/cancel/complete
  GET  /applications/[id]/feedback - Feedback summary
  POST /applications/[id]/decision - Final decision (SELECTED/WAITLISTED/REJECTED)
  GET  /applications/export    - CSV export

RECRUITER ENDPOINTS (/api/recruiter/):
  GET  /applications           - Paginated, filtered list
  GET  /applications/[id]      - Full detail with relations
  PATCH /applications/[id]/status - Status change (validated)
  POST /applications/[id]/notes   - Add note
  POST /applications/bulk-status  - Bulk status update

SHARED ENDPOINTS:
  POST /auth/login             - Login proxy
  GET  /auth/me                - Current user
  GET  /notifications          - User notifications
  PATCH /notifications/[id]    - Mark read

8. AUTHENTICATION INTEGRATION
================================================================================

MAIN SITE INTEGRATION:
- This platform does NOT handle user registration/password storage
- Login proxies to MAIN_SITE_API (env: MAIN_SITE_API)
- Main site returns JWT with user info
- This platform verifies JWT and syncs user from local DB

TOKEN HANDLING:
- JWT_SECRET: env variable (fallback in code for dev)
- Expiry: 7 days
- Storage: localStorage (client) + httpOnly cookie (server)
- Refresh: Manual via refreshUser() on mount/login

ROLE MAPPING (verifyToken):
- Main site roles → Platform roles
- "ADMIN*" → ADMIN
- "LEAD*" → LEAD
- "RECRUITER*" → RECRUITER
- "PANEL*" → PANEL
- Default → CANDIDATE

DEPARTMENT RESOLUTION:
- User.department = String name from main site
- On each auth, lookup Department by name → deptIds[]
- Used for department-scoped queries

10. CONFLICT DETECTION SYSTEM
================================================================================

lib/conflict.ts - hasSchedulingConflict():

ALGORITHM:
1. Find all interviews with status SCHEDULED/RESCHEDULED
2. Filter to those overlapping proposed time slot:
   (existing.start < proposed.end) AND (existing.end > proposed.start)
3. Check panelist conflicts: any assigned panelist in proposed panelists
4. Check candidate conflict: same applicationId

RETURNS:
{ conflict: boolean, conflictingWith: [{ type, userId, interviewId, ... }] }

USAGE:
- POST /api/lead/interviews (schedule)
- PATCH /api/lead/interviews/[id] (reschedule)
- InterviewSchedulerModal shows warnings

12. INTEGRATION POINTS & EXTENSION GUIDE
================================================================================

TO ADD A NEW STATUS:
1. Add to ApplicationStatus enum in lib/status.ts
2. Add transitions in VALID_TRANSITIONS
3. Add role permissions in ROLE_TRANSITION_PERMISSIONS
4. Update Prisma schema comment (line 62)
5. Add StatusBadge color in StatusBadge.tsx
6. Update seed.js if needed

TO ADD A NEW ROLE:
1. Add to Role enum in lib/status.ts
2. Update role mapping in lib/auth.ts verifyToken()
3. Add to requireRoles() calls in API routes
4. Update ROLE_TRANSITION_PERMISSIONS
5. Update useRequireAuth allowedRoles

TO CHANGE DATABASE:
1. Modify prisma/schema.prisma
2. Run: npx prisma migrate dev --name descriptive_name
3. Run: npx prisma generate

TO ADD EMAIL PROVIDER:
1. Modify lib/email.ts getTransporter()
2. Add provider config (SendGrid, Mailgun, etc.)
3. Update sendEmail() for provider-specific options

TO ENABLE REAL-TIME UPDATES:
1. Add WebSocket/SSE server (or use Pusher/Ably)
2. Subscribe in ApplicationTable, LeadDashboard
3. Broadcast on status changes, new notes, interviews

TO ADD DEPARTMENTS:
1. Add to DEPARTMENTS array in prisma/seed.js
2. Run seed or manually insert
3. Create Lead/Recruiter users with department assignment
